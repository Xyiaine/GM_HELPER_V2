A.1 - OBJECTIF DE L'APPLICATION

Créer une application web fullstack permettant à un Maître du Jeu (MJ) de
gérer intégralement une campagne de jeu de rôle sur table dans un univers
post-apocalyptique original : personnages, PNJ, lieux, cités, cartes
interactives, quêtes, objets, rencontres/combats, convois, véhicules,
arbres de compétences, notes de campagne. L'application permet une
utilisation en session live avec mise à jour en temps réel pour les
joueurs.

L'application se compose de DEUX INTERFACES DISTINCTES ET STRICTEMENT
SEPAREES EN TERMES DE PERIMETRE FONCTIONNEL :

  1. INTERFACE MJ (usage principal : ordinateur / desktop)
     -> Accès complet à tout le contenu de la campagne (voir Partie E)

  2. INTERFACE JOUEUR (usage principal : mobile / smartphone)
     -> Accès STRICTEMENT LIMITE (voir Partie F) :
        a) Consultation et édition (si autorisée) de SA PROPRE fiche
           de personnage
        b) Lancers de dés dont les modificateurs sont calculés
           automatiquement depuis SA fiche de personnage
        c) Vue session live limitée (PV, tour d'initiative)
        d) Vue convoi en cours (lecture seule)

IMPORTANT : Le joueur ne doit JAMAIS pouvoir consulter les fiches des
autres joueurs, la base de PNJ, les notes du MJ, les cartes non
partagées, les paramètres des cités, ou tout autre contenu de la
campagne. Le périmètre joueur est volontairement restreint. Ceci est une
contrainte de sécurité et de design non négociable (voir Partie H).

A.2 - UTILISATEURS ET ROLES

- GM (Game Master / Maître du Jeu) : contrôle total sur sa/ses campagne(s).
- PLAYER (Joueur) : accès restreint tel que défini en A.1 et Partie F.

Un utilisateur peut être MJ d'une campagne et joueur dans une autre. Le
rôle est défini PAR CAMPAGNE, pas globalement sur le compte utilisateur.

B.1 - CONTEXTE HISTORIQUE : LE MONDE EN 2200

2050 - Première Guerre Nucléaire
Les grandes puissances s'effondrent. L'explosion initiale rase des
métropoles entières, l'hiver nucléaire plonge la planète dans des
décennies de pénombre. Les survivants se regroupent en enclaves et
bricolent des machines diesel et vapeur.

2100 - Seconde Guerre Nucléaire
Une nouvelle course au carburant et à l'eau dégénère en conflit mondial.
Des zones entières deviennent vitrifiées, saturées de radiations, des
océans s'assèchent. Cette fois, la planète n'a plus de retour possible.

2200 - Le Temps des Cités-Etats
Le monde est un champ de ruines. Les Cités-Etats émergent comme des
bastions de pouvoir, chacune contrôlant une ressource clé pour la survie.

Ce contenu narratif sert de JEU DE DONNEES INITIAL (seed data).

C.1 - VUE D'ENSEMBLE

Application web fullstack monorepo avec :
- /client : Frontend React (Vite)
- /server : Backend Node.js + Express
- /scripts : Utilitaires (extraction lore, fix Prisma)
- /archives : Fichiers archivés

C.2 - STACK TECHNIQUE UTILISEE

--- Frontend (client/) ---

- Framework : React 18 avec architecture par composants
- Build tool : Vite 5
- Gestion d'état : Zustand 4.5 (3 stores : authStore, gmStore, playerStore)
- Routing : React Router DOM 6 avec code-splitting (lazy loading
  sur GmApp et PlayerApp)
- Icônes : Lucide React
- WebSocket client : socket.io-client 4.7
- Pas de framework CSS externe : Vanilla CSS avec variables CSS
  (thème sombre, design system avec tokens)
- PAS de PWA configuré actuellement

--- Backend (server/) ---

- Runtime : Node.js avec Express 4
- ORM : Prisma 6.9 avec SQLite (dev.db)
- Authentification : JWT (jsonwebtoken 9) avec access token +
  refresh token (cookie httpOnly)
- Hashage : bcrypt (12 rounds de salage)
- Validation : Zod 3.24 (schémas dans validators/schemas.js)
- Temps réel : Socket.IO 4.8
- Upload fichiers : Multer (stockage local dans /uploads)
- Sécurité : Helmet 8, express-rate-limit 7, CORS, cookie-parser
- Pas de stockage S3/MinIO : les fichiers sont stockés localement

--- Base de données ---

- SQLite via Prisma (fichier : prisma/dev.db, ~840 Ko)
- Note : le cahier des charges initial recommandait PostgreSQL, mais
  SQLite a été choisi pour la facilité de développement local
- Migrations gérées par Prisma Migrate
- Index sur toutes les clés étrangères et champs de recherche

C.4 - SEPARATION STRICTE DES INTERFACES

Le code respecte la séparation architecturale :

1. Frontend : Deux applications logiquement séparées via React Router
   - /gm/*    → GmApp.jsx (lazy loaded)
   - /player/* → PlayerApp.jsx (lazy loaded)
   Le code-splitting via lazy() garantit que le bundle joueur ne
   contient pas le code MJ.

2. Backend : Deux groupes de endpoints strictement séparés
   - /api/v1/gm/campaigns/:campaignId/...  (20 fichiers de routes)
     Middleware : verifyToken + requireCampaignAccess + requireGM
   - /api/v1/player/campaigns/:campaignId/...  (5 fichiers de routes)
     Middleware : verifyToken + requireCampaignAccess + requirePlayer

3. Les endpoints player ne retournent JAMAIS de données d'autres joueurs,
   de PNJ, de cités, de cartes ou de notes.

C.5 - CONFIGURATION VITE

Le proxy Vite (vite.config.js) redirige :
- /api        → http://localhost:3000
- /socket.io  → http://localhost:3000 (WebSocket)
- /uploads    → http://localhost:3000

C.6 - VARIABLES D'ENVIRONNEMENT (server/.env)

- DATABASE_URL : URL Prisma vers la base SQLite
- JWT_SECRET : Clé secrète pour les tokens JWT
- JWT_EXPIRES_IN : Durée du access token (défaut : 15m)

- PORT : Port du serveur (défaut : 3000)
- UPLOAD_DIR : Répertoire des fichiers uploadés (défaut : ./uploads)
- NODE_ENV : Environnement (development / production)


========================================================================
PARTIE D - MODELE DE DONNEES (SCHEMA PRISMA REEL)
========================================================================

Le schéma Prisma (schema.prisma, 917 lignes) définit 27 modèles :

D.1 - MODELES D'AUTHENTIFICATION

- User : id, email, passwordHash, displayName, createdAt, updatedAt
  → Relations : memberships, characters, diceRolls, vehicleAccesses
- RefreshToken : id, token (unique), userId, expiresAt, createdAt

D.2 - MODELES DE CAMPAGNE

- Campaign : id, name, description, coverImage, gameSystem, gmUserId,
  timestamps
  → Relations : memberships, characters, npcs, locations, quests,
    encounters, items, notes, tags, entityLinks, diceRolls, sessions,
    mapAssets, worldMap, convoys, factions, vehicles, vehicleParts
- CampaignMembership : id, campaignId, userId, role ("GM"|"PLAYER"),
  status ("invited"|"active"), invitedAt
  → Constraint unique : (campaignId, userId)

D.3 - MODELES DE PERSONNAGES

- Character : id, campaignId, ownerUserId, name, race, class, level,
  alignment, background
  Stats de base : strength, dexterity, constitution, intelligence,
    wisdom, charisma (défaut 10)
  Stats de combat : hpCurrent, hpMax, temporaryHp, armorClass, speed,
    initiative, hitDice (JSON), deathSaves (JSON), heroicInspiration
  Compétences : proficiencyBonus, skills (JSON), savingThrows (JSON)
  Classe hybride : traits (JSON), skillPoints, unlockedSkills (JSON)
  Autre : notes, portraitUrl, canBeEditedByPlayer (booléen)
  → Relations : campaign, owner, inventoryItems, combatants, diceRolls,
    vehicleCrewSlots, vehicleAccesses

- CharacterInventoryItem : id, characterId, itemId, quantity, equipped
  → Unique : (characterId, itemId)

D.4 - MODELES DE PNJ

- NPC : id, campaignId, name, race, role, portraitUrl, personality,
  description, locationId, isFavorite, isActive, stats (JSON), gmNotes
  → Relations : campaign, location, questLinks, combatants

D.5 - MODELES DE LIEUX

- Location : id, campaignId, parentLocationId (hiérarchie), name,
  type ("continent"|"region"|"city"|"district"|"building"|"room"),
  description, imageUrl, climate, population, government, notableFeatures
  → Relations : campaign, parentLocation, childLocations, npcs, city,
    questLinks, encounters, mapMarkers

D.6 - MODELES DE CITES-ETATS

- City : id, locationId (unique), health/wealth/technology/food/
  happiness/armament/fuel (0-100), customParameters (JSON),
  specialty, strength, weakness, peculiarity,
  mapX, mapY, factionColor (hex), territoryData (JSON polygone)
  → Relations : location, parameterHistory, questImpacts,
    convoysAsOrigin, convoysAsDestination

PARTIE L - AXES D'AMELIORATION
========================================================================

L.1 - ARCHITECTURE & INFRASTRUCTURE

1. MIGRATION VERS POSTGRESQL
   La base SQLite actuelle est adaptée au développement local mais
   limitante pour la production (pas de connexions concurrentes,
   pas de types avancés). Migrer vers PostgreSQL comme initialement
   prévu améliorerait la robustesse et les performances.

2. MIGRATION VERS TYPESCRIPT
   Le projet est entièrement en JavaScript. TypeScript apporterait
   la sécurité de typage, l'autocomplétion, et réduirait les bugs
   runtime. Prisma génère déjà des types — les exploiter pleinement.

3. STRUCTURATION BACKEND (NestJS ou modules Express)
   Les routes Express sont fonctionnelles mais le code pourrait
   bénéficier d'une couche service plus formalisée séparant la
   logique métier des contrôleurs de route.

4. TESTS AUTOMATISES
   Aucun test unitaire ou d'intégration n'existe actuellement.
   Priorités : tests d'autorisation (un joueur ne peut pas accéder
   aux données d'un autre), tests du calcul de dés, tests des
   impacts de quêtes sur les cités.

5. CI/CD
   Mettre en place un pipeline d'intégration continue (GitHub Actions
   ou équivalent) avec linting, tests, et build automatique.

L.2 - SECURITE

6. LOGGING STRUCTURE
   Remplacer les console.log/console.error par un système de logging
   structuré (Winston, Pino) avec niveaux de log et rotation des
   fichiers. Ajouter la journalisation des actions sensibles.

7. VALIDATION MIME RENFORCEE
   La validation de type MIME actuelle se fie au Content-Type du
   client. Utiliser une librairie de détection de magic bytes
   (file-type) pour vérifier le type réel du fichier.

8. PROTECTION CSRF
   Si les cookies de session sont utilisés sur des formulaires,
   ajouter une protection CSRF (csurf ou équivalent).

9. RATE LIMITING PLUS GRANULAIRE
   Le rate limiting actuel est global. Ajouter des limites par
   utilisateur et par endpoint sensible (création de campagne,
   upload de fichiers, etc.).

L.3 - FONCTIONNALITES

10. EDITEUR DE TEXTE RICHE
    Les notes de campagne utilisent un simple textarea. Intégrer
    TipTap ou Quill permettrait du formatage riche, des liens vers
    des entités, des tableaux, des images inline, etc.

11. BROUILLARD DE GUERRE
    La carte du monde et les cartes locales n'ont pas de système
    de brouillard de guerre. C'est une fonctionnalité clé pour les
    sessions live : le MJ révèle progressivement la carte.

12. EXPORT PDF
    Permettre l'export de fiches de personnage en PDF lisibles,
    formatées, imprimables. Utiliser une librairie comme jsPDF ou
    Puppeteer côté serveur.

13. HISTORIQUE/CHANGELOG DES FICHES
    Implémenter un historique des modifications sur les fiches de
    personnages (qui a modifié quoi, quand). Utile pour le MJ et
    pour éviter les abus.

14. SYSTEME DE QUETES AVANCE
    - Embranchements narratifs (choix A → conséquence X, choix B →
      conséquence Y)
    - Dépendances et prérequis entre quêtes
    - Chaînes de quêtes
    - Templates de quêtes réutilisables
    - Génération automatique basée sur l'état des cités

15. GESTION DU BUTIN AVANCEE
    Tables de loot randomisées, trésors générables par rareté
    et type, loot tables liées aux rencontres.

16. PWA (PROGRESSIVE WEB APP)
    Ajouter un service worker et un manifest.json pour l'interface
    joueur mobile : installation sur l'écran d'accueil, fonctionnement
    offline basique, notifications push pour "c'est votre tour".

17. GRAPHIQUES ET ANALYTICS DES CITES
    Visualiser l'évolution des paramètres de cités dans le temps
    (graphiques linéaires), vue de comparaison entre cités, carte
    thermique des paramètres sur la carte du monde.

18. DASHBOARD MJ ENRICHI
    Le dashboard actuel est basique. Ajouter : widgets de contenu
    récent, checklist de préparation de session, graphiques
    d'évolution des cités, résumé d'impacts de quêtes, alertes
    de cités en état critique.

L.4 - UX/UI

19. DESIGN POLISH
    L'interface est fonctionnelle mais utilise beaucoup de styles
    inline dans les composants JSX. Extraire les styles dans des
    fichiers CSS dédiés ou utiliser des CSS Modules pour une
    meilleure maintenabilité et un design plus cohérent.

20. ANIMATIONS ET MICRO-INTERACTIONS
    Ajouter des transitions sur les modales, les changements
    d'onglets, les résultats de dés (animation de roulement),
    les changements de PV, etc.

21. ACCESSIBILITE (WCAG)
    Ajouter les attributs ARIA, assurer la navigation clavier
    complète, vérifier les contrastes, ajouter les textes
    alternatifs, utiliser du HTML sémantique partout.

22. RESPONSIVE DESIGN MJ
    L'interface MJ est desktop-first mais pourrait bénéficier
    d'un mode tablette (sidebar repliable, layouts adaptatifs).

23. THEME CLAIR OPTIONNEL
    Proposer un thème clair en alternative au thème sombre,
    avec un toggle dans les préférences utilisateur.

L.5 - DONNEES & CONTENU

24. SYSTEME D'IMPORT/EXPORT
    Permettre l'export complet d'une campagne (JSON ou ZIP) et
    l'import dans une nouvelle instance. Utile pour les backups
    et le partage entre MJ.

25. SEED DATA PLUS RICHE
    Compléter les données de seed avec plus de PNJ, quêtes
    pré-construites, et objets pour offrir une expérience de
    démonstration plus complète.

26. GENERATION D'IMAGES IA
    Intégrer un générateur d'images (portraits de PNJ, cartes,
    portraits de personnages) via API de génération d'images.

L.6 - PERFORMANCE & SCALABILITE

27. PAGINATION & VIRTUALISATION
    Les listes (PNJ, objets, quêtes) ne sont pas paginées.
    Implémenter la pagination côté serveur et la virtualisation
    côté client pour les grandes campagnes.

28. MISE EN CACHE
    Ajouter un cache en mémoire (Redis ou simple cache LRU)
    pour les requêtes fréquentes (skill trees, campagne active,
    dernières modifications).

29. OPTIMISATION DES IMAGES
    Génération automatique de thumbnails à l'upload, compression,
    lazy loading des images dans l'interface.

30. STOCKAGE FICHIERS CLOUD
    Migrer le stockage de fichiers vers un service compatible S3
    (AWS S3, MinIO, Cloudflare R2) pour la production.
